# ADR-0001: エンジンに Rust + Bevy を選定する

- **状態**: 承認
- **日付**: 2026-08-01
- **決定者**: ユーザー（選択肢提示に対する裁定）

## 背景

Windows 対応の地球規模フライトシミュレータを、**エージェント主導の開発体制**（オーケストレーター + 8 専門エージェント）で構築する。

エンジン選定において通常最重視される「アセットエコシステムの厚さ」より、今回は **エージェントがビルド・テスト・ベンチマークを人手の介在なしに回せるか** が支配的な評価軸になる。開発体制がそういう形だから。

## 選択肢

| 案 | 長所 | 短所 |
|---|---|---|
| **Rust + Bevy** | 完全コードファースト。`cargo build/test/bench` が CLI で完結。ECS。`f64` 座標系を自前設計できる | 既製アセット/エディタが乏しい。UI とツールを自作する必要 |
| Godot 4 + C# | `.tscn` がテキストで編集可。`--headless` あり。GUI エディタ併用可 | 地球規模スケール（浮動小数点精度・巨大ワールド）で自前対策が必要 |
| Unity 6 + C# | 資産・実機系リソース最大 | シーン/Prefab がエディタ前提。巨大 YAML diff はエージェント編集と相性が悪い。CI が重い |
| TypeScript + Cesium | 実在地形が即入手でき、最難関の要件を一気に回収 | 高負荷時の描画性能に上限。精密 FDM の実行環境として非力 |

## 決定

**Rust + Bevy** を採用する。

決め手は3点。

1. **テスト可能性がそのまま開発速度になる。** `cargo test -p flightsim-fdm` が GUI もアセットもなしに数秒で回る。QA エージェントが回帰網を維持できる唯一の選択肢に近い。Unity 案では実行確認に Editor GUI が要り、エージェントが自律的に閉じられない。
2. **地球規模の座標精度を自前で設計できる。** `f64` ECEF + floating origin という [ADR-0002](0002-coordinate-system.md) の方針は、エンジンの `Transform` が `f32` 固定である Unity/Godot では常に逆らいながら書くことになる。Bevy なら物理層をエンジン型から完全に切り離せる。
3. **モジュール境界を Cargo が強制してくれる。** クレート単位の依存グラフが `Cargo.toml` に現れるので、「FDM がレンダラを参照し始めた」という設計崩壊がレビュー以前にビルドで検出できる。

## 帰結

**受け入れるコスト**
- UI、計器、エディタ系ツールは自作。既製アセットストアの恩恵はほぼ無い。
- Bevy の API は破壊的変更が多い。バージョンを固定し、更新は独立した PR として扱う。
- 3D モデル・テクスチャの調達は別課題として残る（コード生成では解決しない）。

**得られる保証**
- `core` / `fdm` / `world` は Bevy に依存しない純 Rust とする。これは慣習ではなく **CI で検査する規約**（`cargo tree` に `bevy` が現れたら失敗させる）。
- 結果として物理・地形ロジックはエンジン更新の影響を受けず、将来 Bevy を捨てても移植可能。

## 備考

Cesium 案が回収するはずだった「実在地形が即入手できる」利点は、[ADR-0003](0003-terrain-data.md) のオープンデータパイプラインを自前で組むことで代替する。ここは工数を追加で払う判断をしている。
