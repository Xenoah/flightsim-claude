# Exact Filmic reproduction from pinned Blender inputs

The single selected Blender 3.4.1 CPU evaluator reproduces every decoded value of Bevy 0.18.1's `Blender_-11_12.ktx2`. Two fresh evaluator processes give the same 2,097,152 RGBA16F bytes, SHA-256 `b8e2f0a26ee58edda1cf54e591175e8688ae21550e4d16af4c409cfdf5d919dd`. Across 262,144 pixels and 1,048,576 channels, the differing-value and differing-pixel counts, maximum and mean absolute errors, and root-mean-square error are all zero. All three intermediate EXRs and the RGBA32F stream also repeat exactly.

This is an actual computation, not a synthetic successful fixture or a historical-version guess. The reference asset and FlightSim source remain unchanged. The result supplies a concrete reproducible derivation and a specific upstream notice route for the Filmic review. It does not grant publication authority or complete the application's whole-dependency, native, visual or release review.

## Exact reference and evaluator

The reference is [Bevy's Filmic KTX2](https://github.com/bevyengine/bevy/blob/v0.18.1/crates/bevy_core_pipeline/src/tonemapping/luts/Blender_-11_12.ktx2), 308,905 bytes, SHA-256 `a81a2462182bc8499d1a222345a72e7c4f1fabc2cb23d9c543caa567ccba7ad7`, Git blob `db07c847a1879aabe14cbcc1a4d00ec402bc9f1e`. Its path history through v0.18.1 has one introduction commit, [912fb588](https://github.com/bevyengine/bevy/commit/912fb5886908373db2b7c0140ae15961ccd92f72), on 2023-02-19. Its KTX2 header identifies one 64×64×64 RGBA16F level with Zstandard compression and no key/value metadata. The bytes are the actual retained Cargo source asset, checked again after comparison.

The evaluator came from the [official Blender 3.4 download directory](https://download.blender.org/release/Blender3.4/). The 223,772,600-byte Linux archive hashes to `1497f83f93e9bbbde745422c795ed10fe15f92f5622b4421768f149fbe776981`, matching the [official checksum file](https://download.blender.org/release/Blender3.4/blender-3.4.1.sha256). Its executable hashes to `40999207b8b7f8a43a8902535cd6e3a35724b9590cb08715b161c39c5a0119f6` and reports Blender 3.4.1 build `55485cb379f7`, with OpenColorIO 2.1.1.

The GitHub v3.4.1 annotated tag resolves to `ef9ca44dee7fe3e25089dbfc49c69e9eff83ba5a`; that is distinct from the executable's reported build commit. The config, four relevant packaged transform tables, and notice in the official binary package was hashed as a Git blob and exactly matches its counterpart at that pinned tag. The six file identities are in `source-bindings.json`. The original Blender version used by Bevy's author remains unknown; the result does not require asserting that it was 3.4.1.

## Reproduction and comparison

The [unchanged Bevy recipe](https://github.com/bevyengine/bevy/blob/912fb5886908373db2b7c0140ae15961ccd92f72/crates/bevy_core_pipeline/src/tonemapping/luts/info.txt) specifies the stimulus, two colour-space exports, and format conversion. Its linked [stimulus](https://gist.github.com/DGriffin91/e119bf32b520e219f6e102a6eba4a0cf/a9aa0fe151d98ba0f706f8225fce919b1d0fb2b9) uses a 64-sample axis with `i / 64`, exposure -11 through the sampled portion below 12, and middle grey 0.18. It is not an endpoint-inclusive `i / 63` grid. Red varies fastest, then green, then blue. The linked [conversion recipe](https://gist.github.com/DGriffin91/49401c43378b58bce32059291097d4ca/820776c9c34fbc5ce9e9cca868b85441a382897f) converts each RGBA32F sample to nearest-even half precision without rearranging pixels.

The included independently written `stimulus.rs` implements that scalar arithmetic and writes top-row-first RGBA32F. It was compiled by the already installed Rust 1.93.0, commit `254b59607d4417e9dffbc307138ae5c86280fe4c`, Linux x86_64. `run_pinned.py` removes ambient OCIO variables, sets OCIO to the exact bundled configuration before starting Blender, and requires Blender's own configuration-selection acknowledgement. `reproduce.py` verifies the executable and all six input/notice hashes, then invokes image colour management without rendering a scene: export 32-bit EXR from Linear to Filmic sRGB; reload as sRGB and export 32-bit EXR to Linear; read the result and convert to little-endian half precision. The Blender pixel interface's bottom-first row order is explicitly reversed on input and output. Alpha is one throughout; all samples are finite. Factory startup, zero exposure/dither, unit gamma, no look, and no curve mapping prevent unrelated display adjustments.

`verify_reproduction.py` pins the reference container hash and layout, independently decompresses its only level with libzstd, checks every declared generated file against the observation, compares every half-precision bit pattern and numerical value, and rechecks the reference unchanged. The independent reviewer additionally compared Python's standard-library half conversion against the complete output and checked every input coordinate. The two final runs used the explicit pinned-configuration driver and `--python-exit-code 1`. Earlier same-version exploratory runs obtained the same image bytes but lacked the final invocation binding and are not used as the final evidence pair. An earlier setup attempt that lacked the compiler on PATH produced no valid observation and is not counted as a successful run.

The test fixtures in `test_comparison.py` are explicitly synthetic and only exercise comparison failures, including a one-value mutation, signed zero, wrong length, non-finite data, unexpected alpha and wrong reference identity. They are not evidence of the real colour transform.

## Specific source-notice route

The pinned [Blender configuration](https://github.com/blender/blender/blob/ef9ca44dee7fe3e25089dbfc49c69e9eff83ba5a/release/datafiles/colormanagement/config.ocio) attributes the Filmic dynamic-range configuration to Troy James Sobotka and contributors and points to `ocio-license.txt`. The [2017 Filmic introduction](https://github.com/blender/blender/commit/3cd27374ee53bc2ae3fd08b0b73c0a3118f81020) added the same attribution and Filmic tables to that configuration. The [2020 license relocation](https://github.com/blender/blender/commit/0434efa09ddc451675ce8f8e8e7df61f5cc34e89) moved that notice unchanged to [release/license/OpenColorIO.txt](https://github.com/blender/blender/blob/ef9ca44dee7fe3e25089dbfc49c69e9eff83ba5a/release/license/OpenColorIO.txt). Both the historical route and the actual evaluator's notice have been checked.

That notice grants source and binary redistribution with or without modification subject to retention of the copyright, conditions and disclaimer, plus the non-endorsement condition. This supports a documented BSD-3-Clause source-notice route by applying the configuration-level cross-reference to its associated transform tables. The numeric tables have no individual license headers; that scope inference must remain explicit in the exact-asset review. It does not rely on Bevy's umbrella license, Blender's umbrella GPL, or an assumed grant from the separate `sobotka/filmic-blender` repository. Preserve the complete notice and the Filmic attribution with the derivative's provenance. The selected config maps Linear to Filmic sRGB through the two bound Filmic tables and sRGB to Linear through srgb.spi1d. The bound srgb_inv.spi1d describes the reverse sRGB direction and is included as adjacent config evidence; no per-file runtime read trace establishes that it was consumed. No alternative look was selected, and unused installed tables do not create additional obligations.

For history context, the relevant Filmic 1D table has no later change through this tag; the relevant 3D table's only later change is a [header case fix](https://github.com/blender/blender/commit/f405934fe3d31e650cec9af48a4b6c69fd771b1f). This history narrows the derivation but is not used to infer that every older configuration was identical. Exact reproduction provides the material evidence.
