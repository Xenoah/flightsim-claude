# Final supplemental bundle and Windows interaction evidence

Status: prepared local tooling, **no native run or acceptance**. The reduced
Swift-only/Reinhard choice remains pending. These additions generate no positive
dependency review, appearance decision, lifecycle acceptance or publication
receipt. They do not modify the sole stager, ordinary release workflow or any
existing source contract.

## One final bundle identity

The initial qualification's raw collector bundle is useful engineering evidence
but cannot qualify a later notice replacement. The following separate path
keeps the original audited native build and raw inventory immutable:

1. `assemble-analytical-review-notices.py` copies its complete original notice
   tree into a fresh private preparation, then verifies and adds the exact
   candidate texts. The whole-review copy plan and the accepted two-package
   assessment have separate explicitly supplied source roots. Every input is
   hash checked, bounded UTF-8 without NUL, link free and collision free. The
   original inventory bytes are copied unchanged. The output records both the
   candidate plan's old inventory hash and the actual inventory hash; disagreement
   stays visible. Nothing adopts the Linux review hash as native identity.
2. The original transpose function body was mistakenly present in an earlier
   candidate plan. Its exact digest is now explicitly denied, including after
   renaming. Use the corrected 544-file candidate plan plus the 13 two-package
   evidence files. Prepared Rust runtime texts remain conditional until their
   actual native binding is established. Copying them privately does not activate
   a review or permit publication.
3. A separately completed genuine dependency review must bind the final source
   SHA/tree, actual native inventory and exact assembly digest. Its
   `supplemental_evidence_binding` identifies completed source provenance and
   native runtime coverage. Every added file must appear in its hash-bound
   resolution evidence. This tool only consumes such a record; it cannot write
   one. The unchanged readiness checker must permit everything except the
   still-unchecked bundle at preflight. The sole unchanged stager must then
   actually check the staged bundle with that same record and return success.
4. `recheck-reviewed-analytical-bundle.py` consumes the existing frozen build
   capture, completed assembly and genuine review. It performs no application
   rebuild and accepts no new inventory. It calls the unchanged stager with
   `--dependency-review`, reconstructs the exact source/notice/review copy plan,
   archives and freshly extracts those bytes, and runs the same strict runtime
   body used by the first qualification. The extracted readiness invocation uses
   the packaged copy of the identical review record. All four production outcomes
   and all eight fixed Swift captures must succeed, and final source, binary,
   review, archive and extracted-file integrity is checked again afterward.

The final recheck has a one-hour process budget, the existing 180-second capture
watchdog, fresh runtime/fixture directories and a separate bounded text/Swift-PNG
export. `reviewed-bundle.json` binds the original build, assembly, review and
new runtime evidence. A partial run is failed; no partial image set is treated
as final-bundle success. `release_authorized`, `appearance_accepted` and
`distribution_qualified` remain false even after observations complete.

## Modified-source packages

A path patch which is not a workspace member must have a tracked
`analytical-modified-source-provenance.json`. It names the original reviewed
archive checksum/revision, complete current vendor-file manifest, exact reviewed
integration patch, changed paths and retained notices. Origins are restricted
to the two independently assessed zune-jpeg 0.5.15 and bevy_pbr 0.18.1 source
identities. The current tree is labeled `modified_vendored`; an inherited
`.cargo_vcs_info` never becomes a claim that the current source is unchanged
upstream. Its original revision is carried separately, and the unqualified
package `source_revision` is null.

The integration patch may be an addition-only patch relative to production main,
where the vendor tree did not exist. It must not reintroduce removed function
bodies as deletion hunks in public evidence. The full vendor tree and original
member hashes support the separate semantic review. The native projection
validates current bytes; it does not itself certify independent authorship.

Fresh lock, metadata, feature/artifact evidence and notice collection are required
after either patch. Retained source-header spans in changed files need new full
source hashes and offsets; the obsolete removed-body span must disappear. No
routine updates old hashes merely to make validation pass.

## Bounded Windows interaction driver

`observe-analytical-windows-ui.py` accepts only a successful, revalidated final
`reviewed-bundle.json` and that exact extracted executable. It first probes an
interactive Windows Default desktop and the installed local en-US
`Windows.Media.Ocr` engine. The batch evidence workflow records bounded capability
observations after preserving independent frozen-build and platform facts. An
unavailable capability blocks this separate interactive driver while leaving those
facts available for review. No OCR component is installed, no execution/security
policy is bypassed, and no simulator scene is launched by these probes.

The driver launches the production application without instrumentation, binds
its PID/executable/hash, discovers exactly one visible unowned top-level window
belonging to that process, and verifies foreground/ownership before every action.
It sends bounded keyboard and client-pointer messages directly to that HWND.
It never uses global `SendInput`, moves the system pointer, sends to another
application, switches desktops, attaches input queues or synthesizes a focus
policy bypass. These are application message-driven checks, not physical
keyboard/controller qualification.

Map destination selection uses the actual production buttons. Their labels must
be uniquely present in the current client OCR result; clicks use the observed
word bounds and require the client dimensions to remain unchanged. There is no
invented plain-map digit shortcut or fixed guessed screen coordinate. The result
requires the actual selected LAT/LON values in the next capture, not merely a
destination name which is already printed on a button.

Each checkpoint captures only that client's pixels with `PrintWindow` in a
separate helper capped at ten seconds. It never reads the desktop/screen DC.
PNG structure, dimensions and nonblank pixels are checked before local OCR;
OCR is capped at 25 seconds and its word boxes must remain inside the client.
The driver then matches actual UI state and log-prefix witnesses. It records the
exact image, OCR and log-prefix hashes; raw OCR/logs remain private.

The live sequence covers map initial state, actual destination edit, cancel and
reopen, one Swift commit despite repeated Start, pause, editing/canceling a map
opened while paused, resume, restart, all four camera labels, 1024x720 and 640x480
resizes and restoration, one bounded Start/Cancel race, and normal WM_CLOSE with
actual process exit 0. Camera/resize checks run paused to avoid treating an
uncontrolled long airborne interval as a UI test. Their screenshots do not
replace the separate unobscured appearance captures.

The separate legacy sequence uses only the previously verified private replay
fixture, explicit Light/no-model and compatibility opt-in. It checks the full
missing-yaw disclosure through camera/map/resize operations and normal close.
Its images remain private. The frozen partial identity is never upgraded.

The Start/Cancel attempt honestly distinguishes a commit winning the race from
no later commit. Neither outcome alone proves cancellation *during admitted
preparation*. That specific acceptance remains open unless a real observable
preparation/cancellation witness is obtained. Existing source/ECS tests do not
silently substitute for it.

## Actual limits and safe failure

Local Linux checks validate parser, state, copy, provenance and export boundaries
only. Native PowerShell/WinRT availability, targeted event handling, GPU-backed
`PrintWindow` behavior and OCR recognition remain unexecuted. GPU windows can
return blank client captures; that blocks this driver. There is deliberately no
desktop-wide screenshot fallback. A connected interactive Windows executor with
working capture/OCR, or a separately reviewed process-bound Windows Graphics
Capture implementation, is then required. No native capability is claimed solely
because the runner is Windows.

The interaction budget is 20 minutes plus bounded startup/normal-close waits;
at most 128 client capture attempts are admitted. A wrong window, foreground
loss, ambiguous OCR label, changed viewport, missing expected state, runtime
error or timeout stops the sequence. Forced cleanup terminates only the launched
process tree and never counts as normal shutdown.

`ui-observation.json` and fixed-name live Swift client PNGs can be exported only
after revalidation, with a 128-KiB JSON and 96-MiB aggregate budget. Legacy PNGs,
arbitrary text, process logs, OCR text, executables and archives are excluded.
Image exports are evidence for an independent visual reviewer. All appearance,
lifecycle and release-authorization fields remain false. No job invokes the UI
driver automatically before the completed final-bundle review exists.

Relevant platform contracts: Microsoft's [PrintWindow](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-printwindow),
[GetWindowThreadProcessId](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-getwindowthreadprocessid)
and [local OCR API](https://learn.microsoft.com/en-us/uwp/api/windows.media.ocr.ocrengine).

Preparation/verification commands are printed by each script's `--help`;
`observe-analytical-windows-ui.py --describe` is nonexecuting. No invocation,
positive receipt or actual native result is supplied by this document.
